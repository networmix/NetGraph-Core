# E5 — часы Core и реакция P1 на добавленную задержку

Все времена и вычисленные оценки ниже помечены **exploratory**. Часы P1/P2
при восьми workers получены по одному диагностическому процессу без A/B/A:
heavy slot был эксклюзивным, но light work других сессий продолжалась.
Добавлены три one-worker P1 процесса и δ-серия из 63 fresh processes.
У δ-серии есть семь A/B/A triples на каждую δ и воспроизводимые номинальные
95% bootstrap intervals, однако полная квалификация окна RESEARCH §3
не подтверждена по сохранённым machine snapshots; подробности ниже.

P2 отделяет около 1,168 с CPU потоков Core от CPU Python caller. P1 реагирует

около 0,946/1,845 с относительно соответствующих zero-delay controls.
Это реакция на конкретную sleep perturbation, не free-Core endpoint
и не выигрыш от ускорения вычислений.

N = global_span_union_all_phases_s: import/load/prepare/run/export/cleanup,
включая MSD, getters, scoped lifetimes и неизменённые Core calls. Для E1:
observed min–max N = [9,245728938; 9,312738829] с, медиана 9,260524540 с.
Это диапазон трёх наблюдений, не 95% CI. Анализатор утверждает непересечение
фаз перед суммированием. N — raw API-span wall с binding/GIL/bookkeeping cost,
а не чистый solver CPU. Около 0,09 с N (≈1 %) — не Core: чтения часов внутри
spans (~0,065 с) и cleanup span, который включает Python teardown всей модели
и gc.collect (~0,025 с). Это завышает N и занижает f.
N нельзя подставлять в multi-worker gain formula.
Небольшие отрицательные signed clock остатки не являются отрицательным CPU.

**Погрешность и воздействие сборщика.** Single-thread null wrapper стоит примерно
6,31 мкс CPU/call в P1 и 6,19 мкс в P2; inner null span — около 0,165 и 0,161 мкс CPU.
Полная поправка outside вычитает full-wrapper cost минус inner-span cost.
При восьми registered callers плюс main null cost выше: registry snapshots
читают несколько CPU clocks и синхронизируются RLock. Для P1 применение разных
калибровок меняет outside CPU proxy от 1,825155 до 3,089269 с. Это чувствительность
к поправке, не доверительный интервал и не доказанные границы serial работы.
Восьмипоточная поправка к однопоточному Python пути P2 неприменима; отрицательные
значения такой диагностической чувствительности в JSON не являются временем.

Верхнее значение P1 больше всего неинструментированного analysis wall
(2,72 с, медиана δ=0; plain control 2,772 с). Outside CPU — работа под GIL,
и его сумма по threads не может превышать wall, поэтому однопоточная поправка
недооценивает стоимость wrapper как минимум на 0,37 с, а 3,09 с не оценивает
lock-held работу plain run. Полная реакция на δ уже при 0,1 ms (см. «Нормировка» ниже) тоже
не согласуется с насыщенным GIL.

Отрицательные raw outside wall−CPU у P2 объясняются clock-order cost, накопленным
на сотнях тысяч вызовов: span wall включает больше чтений часов, чем span CPU.
После поправки остаются небольшие signed остатки; они не обрезаны до нуля.
Outside CPU содержит Python/runtime, retention и recording, а binding work
с удержанием GIL остаётся внутри spans. RLock ожидания сборщика также могут
попасть в time-not-running. Эта величина включает GIL, futures/queues, native
joins и OS scheduling; отдельное GIL waiting не измерено.

Garbage collection per call (RESEARCH §6, E5) не измерялась: координатор вынес
её из T4 (decisions.md, REVIEW-T4 weighed) в план r2. Clock collector выделяет
память вне spans, поэтому паузы GC в основном попадают в outside CPU,
а не в Core spans (в P2 spans коротких вызовов длиннее 17 мкс занимают вместе
меньше 1 мс).

**Что это говорит об endpoint model.** Ни global span union, ни сумма native
CPU не являются устранимым wall-бюджетом: они содержат ожидания и перекрываются
с outside работой других callers. Даже исправленный outside CPU лишь proxy
в инструментированном расписании. Условия STATE §3 — serial, fixed outside
work на critical path — не доказаны. Прежние условные потолки P1/P3 остаются
условными; новые часы не превращают их в endpoint measurement. Конечный
multi-worker gain не вычисляется.

**Вердикт по RESEARCH §3: полная квалификация окна не подтверждена.**
